# ADR-002: Индекс chromadb пишет один процесс, chroma-сервер

**Статус:** `accepted`
**Дата:** 2026-10-06
**Проект:** obsidian-second-mind

## Контекст
Каждая сессия Claude Code поднимает свой MCP-сервер `obsidian-bridge serve` (05.10 их висело 5), плюс роутер inbox раз в час и CLI. Все открывали встроенный `PersistentClient` на `~/.obsidian-bridge/chroma`. Chroma не рассчитан на запись из нескольких процессов: каждый держит свою копию HNSW в памяти и сбрасывает её поверх чужих записей. 02-05.10 индекс испортился так, что `count()` падал SIGSEGV, роутер падал каждый час.

## Решение
Файлами индекса владеет один процесс: `chroma run --host 127.0.0.1 --port 8777` из venv проекта, LaunchAgent `dev.nzt108.chroma-server` (KeepAlive). `VaultIndex` ходит к нему через `HttpClient` (`OBSIDIAN_BRIDGE_CHROMA_URL`). Сервер недоступен → `RuntimeError` с командой перезапуска, без тихого отката на встроенный клиент. MCP-инструменты записи (`create_note`, `update_note`, `save_insight`) при недоступном индексе сохраняют файл и возвращают предупреждение, а не ошибку: иначе агент повторит вызов и создаст дубль.

## Отвергнуто
- **Файловая блокировка на запись.** Не лечит устаревший HNSW в памяти долгоживущих MCP-процессов: процесс под блокировкой всё равно перезапишет индекс своей старой копией.
- **`watch` как единственный индексатор, остальные только читают.** Читатели всё равно открывают встроенный клиент на изменяющихся файлах, а инструменты записи теряют мгновенную индексацию.

## Последствия
- Новая точка отказа: сервер. Его пульс проверяет Борт (`mac-down:dev.nzt108.chroma-server`), KeepAlive поднимает после падения.
- Эмбеддинги по-прежнему считаются на стороне клиента, модель в каждом процессе своя.
- Тест `tests/test_index_single_writer.py`: 3 процесса пишут параллельно через живой сервер, индекс цел.
